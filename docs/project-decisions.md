# 项目决策

本文记录已经达成、后续实现应继续遵守的项目级决策。字段细节以 [展品数据](schema.md) 和 [素材规则](assets.md) 为准，阶段安排以 [路线图](../ROADMAP.md) 为准。

## 使用独立仓库

Awesome CC98 作为独立代码库维护，不作为现有 CC98 客户端的子包。目录数据、第三方素材、游戏代码、部署节奏和社区贡献方式都有独立生命周期；与具体客户端解耦也能避免把某个实现误认为官方或唯一入口。

## YAML 是编辑源，JSON 是运行时产物

维护者直接编辑 YAML，运行校验和生成流程得到 JSON。这样可以保留适合人工审阅的多行内容和清晰差异，同时让网页与游戏读取严格、统一且不需要 YAML 解析器的产物。

- 不手工维护与 YAML 平行的第二份 JSON 数据。
- 运行时消费者只读取生成且校验通过的 JSON。
- JSON 不承载新的事实；需要修改内容时回到对应 YAML。
- Schema、跨文件引用和生成一致性共同构成发布边界。

## 目录各自拥有不同信息

- `exhibits/<id>/exhibit.yaml`：作品事实、来源、作者、状态、平台、关系和展品专属素材。
- `collections/*.yaml`：某个出口选择哪些展品、如何分组和排序。
- `ASSETS.yml`：候选素材以及博物馆共享的已批准本地素材。
- `assets/`：角色、家具、贴图、音效、共享作者头像等已登记文件。
- `scenes/*.yaml`：二期游戏的房间、坐标、展品引用和交互配置；目前尚未建立。
- `generated/`：构建生成物，不作为人工编辑源。

展品事实不能复制进集合或场景；这些文件只通过稳定展品 ID 建立关系。

## 目录、视觉和游戏分层

目录先于具体展示界面存在。README、普通画廊和 2D 博物馆可以采用不同的策展顺序和交互方式，但共享同一份展品事实。游戏场景改变不应迫使展品数据迁移，展品状态更新也不应要求手工同步多个页面。

## 素材采用两阶段生命周期

1. 候选阶段只记录远程位置、作者、权利与隐私调查，保持 `publish: false`，不被产品读取。
2. 入库阶段才下载文件，并登记来源、作者、权利依据、署名、隐私复核、哈希和发布状态。

公开 URL 或公开 GitHub 仓库只能证明来源可访问，不能单独证明允许再分发。作者许可、适用许可证、自制或生成记录才是本地入库依据。署名是履行授权要求和保存作品历史的一部分，但不能代替授权本身。

## 保留必要的公开作者身份

作者主动公开用于作品宣传的用户名、头像、项目署名和品牌水印可以保留，并记录原位置、作者和署名。项目维护者已经逐一向相关创作者确认，本轮收集的 CC98 头像和 GitHub 头像可以直接使用；README 和后续产品对全部头像统一显示账号署名、主页链接和关联作品。README 在同一作者有多个头像时优先使用 GitHub 头像，再回退到 CC98 头像；运行时素材清单继续保留全部已批准版本。

以下边界继续有效：

- 与展品无关的背景用户名、头像和真实帖子内容遵循最小化原则，必要时裁切、打码或用模拟数据重制。
- 私信、非公开帖子、IP 地址、密码、令牌、登录凭据、会话标识和个性化追踪水印不得进入仓库。
- 作者主动添加的公开署名水印可以保留，不能与个性化追踪水印混为一谈。

## 网络素材与生成素材使用同一套可追溯要求

网络下载素材记录原页面、直接资源地址、作者、许可证或许可、获取日期和必要署名。自行绘制或通过图像工具生成的素材记录创作者或工具、提示词、生成日期、后续编辑和发布条款。派生裁切、压缩、格式转换和背景移除也要能追溯到原素材。

## 2D 博物馆采用数据驱动场景

游戏不会把展品内容硬编码在地图或组件中。场景只引用展品与素材 ID，并描述位置和交互；标题、作者、来源和状态从生成目录读取。这个边界使普通目录可以先发布，也使展厅能够独立迭代、复用素材和增加彩蛋。
